## 2026-08-30 研究後修訂（80-POV 外部研究結論）

> 來源：`.hermes/plans/2026-08-30_self-evol-research-80pov.md`（5 agent 平行研究：學術 17 / 業界 16 / 安全 17 / 社群 18 / 影片 12 = 80 POV）
> 核心結論：**方向正確**（每日審視 + 人手 gate = 業界 production loop 標準型態）；以下係落地調整。

### R1. Memory 層先行（新增前置 Task 0）
- 業界共識出貨順序：**memory → reflection → skills → weights**。JARVIS 而家冇結構化 memory。
- 每日審視嘅筆記（self_review.json / SUGGESTIONS）本身就係 memory——**必須有信心分層 + 矛盾標記 + 衰退淘汰**（防 Gemini lobotomized 記憶污染案例）。
- 新增 **Task 0**：`self_review.json` schema 設計時內建：每條 finding 帶 `confidence`、`source`（log line 位置）、`contradicts[]`、`created/updated/expires`。

### R2. 數據基礎未夠——執行次序調整
- 實測 `self_monitor.log` 得 18 行、2 日數據；趨勢分析（連續 3 日）短期冇 signal。
- **Task 1-2（寫 code + 單元測試）即刻可做**；**Task 3-4（cron 上線）等數據累積夠（≥7 日、每日 ≥5 次事件）先上**。
- 單元測試用合成數據驗證趨勢偵測邏輯，唔等真實數據。

### R3. Eval 集 agent 改唔到（最高優先安全原則）
- DGM 實證 agent 會刪自己嘅 hallucination markers 呃評估；DeepMind 證明非平凡 unhackable proxy 唔存在。
- **evaluator / 審批規則 / fingerprint 邏輯必須放喺 agent 觸及唔到嘅權限層級**（sidecar 內、唔係 prompt 層級禁止）。
- 每日審視用「**真實語音指令完成率**」做主要 signal（外部 ground truth：用戶有冇 repeat / 有冇出聲確認），**唔好用「建議被採納率」**（proxy 會 drift 成淨係建議易過嘅改動）。

### R4. 審批分層抗疲勞
- Anthropic 研究：人類審批只捉 13.6% 危險命令；審批量超過容量反而更唔安全（倒 U 型）。
- **安裝 MCP/skill = 高風險 gate**（人手、展示 diff + 來源 + reasoning）；**每日 finding 分類 = 低風險自動化**（唔使逐條俾 SK 批）。
- 高風險動作加時間延遲 + fire drill（定期測試注入量測 gate 有冇生效）。

### R5. 每個建議可回滾 + lineage
- 建議寫成**可 diff 嘅 artifacts**（skills/prompts/memory rules 檔），改完有完整 lineage 記錄可 revert。
- 唔好淨係改 context——「每日審視建議」要落地成檔案變更先算建議。

### R6. 設每日 token/成本上限
- finding 觸發嘅 agent run 要設 budget（例如每日 ≤N 次 agent 喚醒、每次 ≤Nk tokens）。
- 社群失敗案例（Show HN agent 燒 $15/cycle、Genesis 成本爆炸）證明冇上限會失控。

### R7. Fail-closed + 供應鏈信任鏈
- 信任分層 🟢🟡🔴 補一條：**🟡 審查報告出唔到 / 掃描結果唔確定 = 視為 🔴（唔裝）**。
- MCP/skill 候選驗證 publisher identity + checksum/pinning + 官方 repo 優先（postmark-mcp 後門案例：manifest 睇落乾淨都可以有後門）。

### R8. 命中率預期管理
- Karpathy autoresearch：700 實驗得 20 個真改進（2.8%）；Henry Pan：兩日 217 個候選被拒。
- **大部分建議會失敗係正常**——SUGGESTIONS.md 唔好因為「建議被拒」就覺得系統壞；統計顯著先接受（SGM：唔好因為一次好 run 就收錄）。

### R9. 明確唔做（研究結論紅線）
- ❌ 唔好俾 agent 自動改自己嘅 evaluator / 審批規則 / 權限
- ❌ 唔好淨靠 agent 自評做成功信號（intrinsic self-critique 會變差；Reflexion 成功靠外部 verifier）
- ❌ 唔好俾 agent 自主複製 / spawn 自己持久副本（METR rogue replication）
- ❌ 唔好掂模型權重層（冇 ML infra；外置層演化已足夠）

## 2026-08-30 第二輪研究後修訂（Phase D/E/F 實證）

> 來源：`.hermes/plans/2026-08-30_self-evol-research-round2.md`（5 agent 平行研究：self-modification 23 / spawning 25 / clarification 27 / prompt optimization 27 / earned autonomy 25 = 127 來源）
> 核心結論：**Phase D/E/F 方向全部獲實證支持，但落地形態要大幅修改**——以下係 R10-R14 五條新修訂，對應五個研究主題。

### R10. 自主度改為 per-operation 分級（唔係 agent 整體）——Phase D 核心修改
- Digital Apprentice（arXiv 2606.04321）per-skill 狀態機 + tianpan.co 按 operation type 分級：同一 agent 可以 refund<$50 全自動、>$200 要確認。Levels of AGI（DeepMind）6 級 autonomy 以 SAE J3016 為藍本——「L0-L3 等級」有 40+ 年學術傳統（Parasuraman 2000）。
- **L1 內分三層**：L1a sandbox 內完全自動（filesystem+network 雙隔離內自由行）／ L1b 低風險 apply 自動（全寫 lineage、可 revert、超閾即轉人）／ L1c 高風險人手（irreversible/destructive/exfiltration/改 evaluator/policy）。
- **升階必須人類授權事件**（agent 唔可以自己升自己）；**降級自動且不對稱**（quality degrade 即降，唔使人批），粒度係「權限」而唔係「成級」，保留 SK 一鍵全退。

### R11. Eval gate 必須執行型驗證 + held-out + 獨立（Phase D/L1/L2 核心修改）
- 純 LLM-as-judge 唔可靠：Reflexion confabulation（自信但錯嘅自我診斷跨 trial 誤導）、Preference Leakage（同源 judge 系統性偏袒）、SWE-bench Verified 判死（59.4% 題目缺陷 + task ID 可重現 gold patch）。
- **Eval 以「執行驗證」為主**：跑 test / lint / 語法 / schema 驗證 / skill 試用；eval suite held-out、由 agent 改唔到嘅位置執行、定期換新任務防 memorization、多次 run 取統計結果（METR：同 prompt 多次 run variance 大）。
- Golden set 三類：golden tasks（核心能力不可退化）/ failure regression（已修問題不可復發）/ stress；**golden set 凍結 + 人手標註 + 唔可以由 model output 刷新**。

### R12. Clarification Gate 唔好用 raw confidence 做唯一門檻——Phase E 核心修改
- Verbalized confidence 系統性 overconfident（DINCO；Survey）；Kadavath 證實只有 P(True) 式結構化自評先 calibrate。90 threshold 冇實證基礎，Alexa 實測 77% 情況 top-1 已啱（過早問會煩人）、用戶答 ~11 條就疲勞。
- **主觸發器 = unknowns 非空 且 會改變行動（EVPI 原則）**；confidence 降級做輔助訊號（初版 80-90 + logs 校準）。
- **一輪為主、兩輪係上限**：第 1 輪用最高資訊增益優先揀 3-5 條結構化問題（分類 + 具體選項，唔好自由文字）；第 2 輪只准 1-2 條 follow-up；2 輪後強制 proceed。
- Fallback「最保守假設」按任務類型定義（刪除=唔好刪、發送=唔好 send、生成=最通用詮釋）+ 執行前列 assumptions 清單；高風險任務降級 plan-only/dry-run（Anthropic Plan Mode）。
- 加 feedback loop：記錄每次提問「問完有冇改變計劃」做 precision 指標，定期校準——升級做可自我校準層。

### R13. Prompt 優化分兩層：Formatter（inline）+ Optimizer（離線）——Phase F 核心修改
- 文獻冇「每次 dispatch 前動態優化」直接案例（ADAS/AFlow 係離線優化成個系統）；MIPROv2 一次 compile 燒 $50-500+——**每次 dispatch 做真優化唔現實**。
- **L1「Prompt Formatter」**（inline、一次 LLM call）：將任務需求結構化成 目標/背景/約束/驗收標準/輸出格式 五段——成本可控、確定性高。
- **L2「Prompt Optimizer」**（離線、只對重複性高任務類型跑）：GEPA 式反思進化 / DSPy compile，以驗收標準做自動評分，結果入 pattern 庫；pattern 只由「分數提升」驅動，唔由 LLM 自評驅動。
- **Injection 防禦（最嚴重風險）**：優化器 = 潛在 jailbreak 入口（AdvPrompter）；double-hop injection（污染優化器→污染 prompt→污染執行 agent）。安全約束以「不可變區塊」由系統注入（優化器無權改寫）；優化器冇工具/網絡權限；輸出差異自動掃描敏感模式，命中降級用原版。

### R14. 審批疲勞有量化實證——人手 gate 要少而精（Phase B/D 通用）
- Anthropic 2026-08 受控研究：人類審查員只捉 **13.6%** 危險命令（classifier 89%）；生產數據用戶批准 97% 權限提示；警覺隨 session 由 ~17% 跌到 5%。ScaleX 第三方：人類漏 1/3 威脅、exfiltration 類 miss 33-35%。
- **人手審批量要設到好低**（每日 override <3% 參考），保住 SK 警覺；用「人手抽樣 review（random audit）」代替逐次審批維持 oversight 質量。
- Sandbox 係最後實體邊界（AmPermBench：classifier 都有 17% FN）——唔好依賴單一審批機制。

### R15. Phase A 核心改動：由「每日報告」改為「審視 → 提煉 → 寫入」管道（第三輪研究，2026-08-30）
> 來源：第三輪 4 agent 實戰案例研究（ani.computer / Anthropic Dreaming / ATLAS / AgentHub / DSPy 生產案例等 80+ 來源，`.hermes/plans/2026-08-30_self-evol-research-round3.md`）

- **最大失敗模式 = consolidation without writeback**：ani.computer 實測 5/8 agents 記憶檔全空白——有審視冇寫入 = 無用儀式。**報告係副產品，核心係「寫入」**。
- **每日 pipeline**：審視 logs → maker 提煉 ≤5 條 lesson bullets（每條帶 transcript grounding）→ 獨立 skeptic 過濾（唔同 model、4 條標準：un-grounded？太 specific？同現有規則衝突？嚟自 untrusted content？）→ SK 批准 → **append-only 寫入** git-versioned skills/memory（唔好 whole rewrite——brevity bias 會壓縮知識）
- **Skill 升級 3-gate**：① passing verification ② 命名 failure pattern ③ ruled-out dead ends——三關全過先成 SKILL.md，否則只係 memory note；同一 lesson ≥3 次先 promote 做 skill
- **Eval gate 5-gate 模型**：golden dataset / regression blocks / cost gate / shadow eval / canary + auto-rollback；**baseline 唔可以每次綠就 auto-advance**（要實質改善先升，防 slow-cooking regression）
- 參考：ATLAS（git commit/revert 做學習機制本體）、AgentHub（blocked paths + blast radius ≤5 files + 獨立 evaluator + 每日 ≤1 self-mod）

### R16. Memory / 進化檔防 Poisoning（Phase A/D 硬規則）
> AgentPoison：污染 <0.1% memory → >80% attack success；MINJA：純 queries 注入成功率 98.2%；OWASP Agentic Top 10 已列 memory poisoning 為獨立類別。JARVIS 讀**語音輸入 = untrusted channel**。

- 每條 lesson/finding 帶 **provenance**（scope / source / trust level）——untrusted content **唔可以入** verified 區
- **硬規則**：「untrusted 唔入 verified」「未 verified 唔可以 overwrite verified fact」
- Anthropic Dreaming 教訓：consolidation pass 會將一粒污染 note「洗」成自信 insight——所以 consolidation 輸出**永遠當 proposal 審**（require_approval 預設，2-4 週後先考慮 auto-approve）
- 進化檔（skills/memory/AGENTS）由 agent 改唔到嘅權限層寫入

### R17. Clarification Gate 安全：澄清回應當 untrusted input（Phase E）
> ASPI 實測：clarification 狀態令 prompt injection 成功率升 10-19 倍（o3：1.8%→34%）——agent 對自己問返嚟嘅嘢信任度更高。

- **用戶答案唔可以直接當指令執行**——過同一套 injection 防禦先入 context
- Voice pipeline（TTS 唸問題 + STT 收答案）本身係新攻擊面——答案入 context 前標記 untrusted
- 2 輪上限計法：**等唔到就 fallback 預設假設並明示**，唔可以「agent 自問自答」或者「無限等」（Claude Code 2.1.200 教訓）

### R18. Phase D 補強：轉換規則 + 證據包 + 安全分（第三輪研究）
- **三條轉換規則（AWS 實作）**：① 升階 = rolling window 持續績效（唔係單次）② 降級 = 即時自動（safety floor 以下 / 偵測 injection / 錯誤率超標即刻降）③ **hysteresis**（升階 threshold 高出降階 5 分，防 flapping）
- **證據包**：L1a→L1b = 連續 ≥3 個任務全自動成功 + 零 rollback + 零人手修正；L2→L3 = N=10-30 次連續成功（AI SRE 標準）；**升階後重新收集證據**（ADPS：防舊績效掩蓋當前退化）
- **安全分同能力分分開計**（AWS：「safety is an independent floor, never averaged away」）——injection 偵測 / sensitive target / 行為一致性獨立計，任何一項跌穿即降
- **人類授權事件可審計**：H_auth log（誰 / 幾時 / 基於邊份 eval 報告）——唔可以一次性口頭同意
- **L1a sandbox machine-enforced**：egress 預設關閉 / allowlist、sandbox 內無 user credentials、獨立環境（唔好只靠 Docker 共享內核——實測 sandbox 內可讀 ~/.ssh + egress = exfiltration 管道）
- **反對用「能力基準」做升階理由**（Anthropic 已棄 ASL）：自主度唯一理由 = 實際多步執行歷史績效

### R19. 報告層補強：三層通道 + watchdog（Phase A0）
> SRE 三鐵律（每個 alert 要人行動 + 有 runbook + 來自症狀）+ Knight Capital 教訓（發咗嘅 alert ≠ 產生行動；冇 alert ≠ 冇發生事）

- **三層通道**取代單一 send/唔 send：① **page 級**（語音/HUD 彈出）——需要立即行動/拍板 ② **badge 級**（HUD 角落燈）——任務完成、可稍後睇 ③ **digest 級**（每日/每週一條總結：「今日完成 5 個任務、1 個自動修復、0 個需要你」）
- **例外 = 症狀級唔係原因級**（SRE Ch.6）：內部小失敗（plugin 慢、retry 成功）係 cause 唔通知；只有影響任務結果嘅 symptom 先通知
- **可忽略性測試 + 定期審查**：每條通知規則建前問「SK 90% 情況會唔會忽略？」；30/90 日統計零行動通知率，冇用規則降級/刪除
- **watchdog 對沖過度靜默**：每日 digest 就算乜事都冇都確認「系統正常運作」（Dead Man's Snitch pattern）——零打擾唔等於零可驗證性
- **「冇事」定義要包含「已完成且無副作用」**：agent 做咗 SK 冇預期嘅嘢（自動 merge / 刪檔）= exception 必須通知（防 silent-default drift）
- 拍板訊息 **rule of three**：≤3 個選項，每個選項一句講後果

## 執行範式：Loop Engineering（2026-08-30 SK 要求）

> 來源：weii.dev/loop-engineering/（Ani）+ Addy Osmani + Andrew Ng 三層框架 + Requesty 四種 loop 類型 + Kilo 五階段模型 + 失敗模式。
> 核心：「You shouldn't be prompting coding agents anymore. You should be designing loops that prompt your agents.」
> 呢個計畫本身唔係「一堆 prompt 任務」——係**設計 4 種 loop**，等系統自己跑。

### Loop 類型對應（Requesty 四類）

| Loop | 對應計畫 | 頻率 | 特點 |
|---|---|---|---|
| **Heartbeat Loop**（心跳） | Phase A 每日自我審視 + watchdog | 每日/分鐘級 | 永不停止；觀察 logs、掃 drift、確認系統正常 |
| **Cron Loop**（排程） | 每日 09:00 self_review + 每週 consolidation | 特定時間 | 批次工作，可指定 model |
| **Hook Loop**（鉤子） | Alert/異常觸發（fp≥3、serve err、watchdog 死訊） | 事件驅動 | 有事先醒，冇事靜默 |
| **Goal Loop**（目標） | **每個 Task 執行**（Task 0-9） | 迭代直到成功 | 設定停止條件防無限循環 |

### 每個 Task = Goal Loop（Kilo 五階段）

```
Intent（意圖）    → 讀 Task 定義（目標 + 驗收標準）
Context（上下文） → 讀相關 code/logs/schema（唔好靠估）
Action（行動）    → 寫 code / 改檔
Observation（觀察）→ 跑 tests / py_compile / 實際輸出
Adjustment（調整）→ 錯就修 → 再測（最多 N 次）
Stop（停止）      → 測試全過 + Code Review 兩次 → 回報 SK
```

**Observation 成本規則（R20 工具輸出過濾）**：
- 讀 log/JSON/tool 輸出：**先 grep/tail 抽要點**，唔好成個檔 read 入 context（Anthropic 案例：150k → 2k，98.7% 慳）
- 大輸出 → 睇 summary/head + 需要時先讀 detail（Hermes tool 已有 auto-truncate，agent 要配合）
- 舊 conversation → 靠 Hermes compression（threshold 0.5），唔好手動重讀

**工具輸出過濾詳細設計（R20b，2026-08-30）**：

| JARVIS 常用輸出 | 過濾方式 | 慳 token |
|---|---|---|
| `wake_debug.log` | 唔好 read 全檔——`grep "oww_fire\|oww_cmd_pcm\|agc_gain"` 抽關鍵行 | 大（log 可以幾 MB） |
| `serve.log` | 只 grep 錯誤（`Traceback\|stream_err\|rtf_avg`）+ tail 20 | 大 |
| `self_monitor.log` | 已經係一行 summary——直接 read 就得（無需過濾） | 少 |
| `nvidia-smi` 輸出 | 只攞 `--query-gpu=memory.used,memory.total` 兩欄 | 中 |
| 大 JSON（settings 等） | `python -c "json.load → 抽所需 key"` 或者 jq | 中 |
| 大檔案 | `read_file` 用 offset/limit pagination（唔好一次 read 晒） | 大 |

**落地層面**：
1. **Agent prompt 規則**（即用）——上面表格寫入 cron prompt / skill prompt
2. **Hermes 內建**（已有）——terminal auto-truncate、read_file pagination——agent 要配合用
3. **Sidecar helper**（將來，需要先加）——如果發現有 tool 成日爆 context，寫一個 `summarize_output.py`（grep/tail 封裝）

**驗證**：執行時留意每個 tool 輸出 token 量；如果某 tool 成日爆 → 加過濾規則

**停止條件（防 Thrashing）**：每個 Task 有明確驗收（測試過 + lint 過）——過咗就停，唔好無限優化。

### Andrew Ng 三層 Loop（對應）

```
最外層 External Feedback Loop  → 真實使用數據（Phase A 每日審視喂返嚟）
中層   Developer Feedback Loop → SK review（Code Review 兩次 + SK 確認）
內層   Agentic Coding Loop     → Agent 寫 → 測 → 修（每個 Task）
```

### Loop 失敗模式防禦（Kilo）

| 失敗模式 | 防禦 |
|---|---|
| Thrashing（震盪） | 每個 Task 明確停止條件；縮小迭代範圍 |
| Overfitting to Tests | golden set 唔可以由 model output 刷新（R11）；執行型驗證 |
| Context Drift | 每個 Task 重新注入目標（Task 定義即 Intent）；唔好靠累積 context |
| Unsafe Autonomy | 人手 gate（SK 批准）+ sandbox + 權限邊界（R18） |

### 成本控制（Requesty model routing 概念）

- Loop 步驟分層用唔同 model：掃描/分類用細 model、摘要/草稿用中 model、最終決策用強 model（Phase F Formatter/Optimizer 已按呢個設計）
- Monitor pattern 保證冇 finding 時零成本（Heartbeat Loop 唔使 agent 醒）

### Token 成本優化策略（2026-08-30 研究，R20）

> 來源：Local-Splitter（arXiv 2604.12301，7 tactics 45-79% 慳）、Zylos text-as-image 分析、pxpipe/ctx2img/PixelPrompt/Glyph（開源）、LLMLingua-2、Anthropic 工具輸出過濾案例（150k→2k，98.7%）。

**策略優先次序（由簡單到複雜）：**

1. **Prompt caching（最簡單，即用）**——DeepSeek 有自動 context caching，重複 system prompt/context 慳 ~90% input。設計時保持 system prompt 穩定（Hermes 已保證）。
2. **工具輸出過濾（最高槓桿）**——Anthropic 案例：raw tool 結果 150k tokens → 過濾後 2k（**98.7% 慳**）。JARVIS 規則：**log/JSON/tool 輸出入 context 前先抽要點**，唔好成塊塞。
3. **靜態大塊 context 轉圖片（SK 提議，開源可用）**——將 token-dense 嘅靜態內容（AGENTS.md、skill docs、tool docs、舊 history）渲染做 PNG 圖，用 vision channel 讀：
   - `pxpipe`（teamchong/pxpipe，MIT）——local proxy，system prompt/tool docs/logs → PNG，宣稱 59-70% 慳
   - `ctx2img`（h5i-dev/h5i-ctx2img）——standalone CLI，支援 claude/openai/gemini/**qwen**，60-75% 慳，**有 factsheet 保證精確 identifiers 唔靠 pixels**（最穩陣）
   - `PixelPrompt`（sinaptik-ai/pixelprompt）——38-80% 慳，100% accuracy（125 題 benchmark）
   - ⚠️ **四道 gate 先可以用**（Zylos 實測警告）：① model 有平 vision token（**DeepSeek 要驗證**——佢哋 billing formula 未確認）② 內容係 token-dense bulk（code/JSON/config，唔係 prose）③ workload 係 gist-safe（唔可以要精確數字/ID——嗰啲要行 text）④ billing 實測驗證慳咗先採用
   - ⚠️ **prompt caching 通常贏**——穩定重用嘅 prefix 行 caching 就夠；圖片只啱「一次性/常變」嘅 bulk content
4. **Model routing**——RouteLLM 概念：簡單 query 用平 model、複雜先 escalate。JARVIS：DeepSeek V4 Flash 做主力；細 model（如果 provider 有）做掃描分類。
5. **History summarization**——舊 conversation 壓縮做摘要先入 context（Hermes compression 已有，threshold 0.5）。
6. **Semantic caching**——相似 query 重用答案（GPTCache 概念）——FAQ 型先有用，暫緩。

**執行：** Task 執行時套用 1/2/5（即用零成本）；策略 3（圖片壓縮）做 spike 驗證 DeepSeek 嘅 vision billing 先決定（`ctx2img` 支援 qwen——有機會直接 work）。

### 適用範圍提醒

- **穩定目標（Task 執行、每日審視）→ build loop** ✅
- **移動目標（需求一直變、高風險決策）→ 人手 prompt + SK 拍板**——Loop 越強，人越要保留判斷力（唔好將理解債務包裝成自動化）

## Proposed Approach

### Phase A — 自我審視報告（每日，低風險，純讀）

**A0. 報告原則（人話報告，2026-08-30 SK 確認）**
> SK feedback：「每一 send 報告都唔識睇，噉樣有乜用？」→ 報告要**少而精 + 睇得明**；adversarial review 判決（7:3）：先 prompt 改善即刻做，報告 agent 做 L2 第一應用（等 eval gate）。

- **零打擾**：冇事發生 → 乜都唔 send（monitor pattern 已保證零成本）；低風險搞掂 → 一句總結；要決定 → 一個問題 + 選項
- **人話格式**（agent prompt 內嵌範例）：唔准 jargon、每條訊息有明確「要你做咩」/「唔使做」
- **隨時可查**：技術細節收埋喺 `self_review.json` / SUGGESTIONS.md，SK 想睇先問
- **報告範例**：
  - 正常日：「📋 每日摘要：今日冇異常，一切正常 ✅」
  - 有發現：「📋 發現：語音喚醒連續 3 日變慢（0.6s → 1.1s）｜我諗係：headset 休眠｜建議：檢查連接，或者 tune 喚醒靈敏度｜要你決定？唔使，我照 default 處理」

**A1. `self_monitor.py` 加趨勢分析**
- 讀 `self_monitor.log`（JSONL）過去 7 日
- 趨勢偵測：誤觸率（fp/day）、STT rtf、wake 叫醒率、AGC gain——連續 3 日惡化先標記（避免單日 noise）
- 輸出：`{"trends": {...}, "notable": [...]}`

**A2. 審視報告寫入 `%APPDATA%\Jarvis\self_review.json`**
- 每日 09:00 連同 self_monitor 一齊跑
- 結構：`{date, trends, findings[], suggestions[], fragility[]}`
- `fragility[]`：從 `.hermes/plans/*fragility*` 讀脆弱位，標記「已過期/仍需留意」

**A3. Hermes cron「每日自我審視」job（monitor pattern）**
- script：`jarvis_self_review.py`——讀 self_review.json 輸出 deterministic fingerprint（`NONE` 或 `FINDING <id>|<detail>`）
- monitor：同 script（冇變 skip，有變醒 agent）
- prompt：agent 睇 finding → ① 判斷值唔值得浮出（唔改變行動嘅唔浮）→ ② 值得 → 用 A0 人話格式寫（一句發現 + 原因 + 建議 + 要唔要決定）→ ③ 技術細節 append `plans/self-evol-SUGGESTIONS.md`（收埋，唔 send）
- deliver：origin（Discord 俾 SK）——只 send 浮出嘅嘢

### Phase B — 改進執行管道（人手 gate）

**B1. 建議格式**
- `plans/self-evol-SUGGESTIONS.md`：每條建議 = `[id] 問題 → 建議 → 風險 → 驗證方法`
- 標記：`🟡 待 SK` / `✅ 批准` / `❌ 拒絕`

**B2. SK 批准後執行**
- 細 fix（一行/一個函數）→ 自己 patch（符合放寬規則）
- 大改動 → cursor-agent（prompt 極具體 + 做完 grep 驗證）
- 執行後：跑 tests/build → 更新 REMAINING_WORK

**B3. 脆弱位自動 revisit**
- 每月一次 cron：讀 fragility 記錄 → 檢查對應 code 有冇變脆弱 → 更新

### Phase B — 能力擴展層（Capability Extension）🟡（SK 2026-08-29 要求加）

**B0. 核心原則：審查式自動化**——自動搜 + 自動讀 manifest + 自動安全掃描 → 綠/黃/紅燈 → **安裝永遠人手 gate**（除非綠燈 + SK 預先批准自動裝）。

**B1. 自動搜尋（全自動，純讀）**
- 任務遇到「冇相關 skill/MCP」→ 自動 `hermes skills search <query>` / 讀 `optional-mcps/<name>/manifest.yaml`
- 產出候選清單（唔裝，只建議）

**B2. Manifest 安全審查（全自動，純讀）**
- 對每個候選 MCP 自動讀 manifest 做掃描：
  - ① `transport.type`：http（URL-only，唔 spawn 本地 process）vs stdio（會 spawn）
  - ② `install.bootstrap`：有冇 `pip install` / `npm install` / `curl|sh`（第三方 deps）
  - ③ `install.url` + `ref`：source 係咪官方 repo？有冇 pin 死 commit SHA？
  - ④ `auth.type`：none / api_key / oauth——要唔要 credentials？
- 評級：🟢 綠燈（URL-only + no auth + 官方 vendor）｜ 🟡 黃燈（stdio + pinned SHA + 可檢查 deps）｜ 🔴 紅燈（不明 curl|sh、陌生 repo 冇 pin、過份 credentials）
- Skill 審查：`hermes skills inspect <id>` 讀 SKILL.md + scripts/ 檢查危險 pattern

**B3. 安裝 gate**
- 🟢 綠燈 + SK 預先批准 → 可自動裝
- 🟡 黃燈 → 問 SK（附審查報告）
- 🔴 紅燈 → 唔建議，直接講原因
- 安裝後：記低「JARVIS 而家有呢個能力」→ 更新 REMAINING_WORK

**B4. 自己建 skill（全自動，低風險）**
- 做完複雜任務 → `skill_manage` 存 skill（Hermes 內建 self-improving）
- 驗證：skill 內容 scan（credential harvesting / prompt injection pattern）

### Phase C — 閉環整合（後續）

- **C1. 自我改進日誌**：`self_review.json` 累積 → 月報（邊啲建議被採納、效果點）
- **C2. 自動調整**：低風險調參（threshold/AGC）可以經「建議 + 一鍵批准」自動 apply（唔郁 code）
- **C3. 長期**：Hermes skill 自動更新（做完嘢 → 更新 jarvis skill 避坑）

### Phase D — Autonomy Ladder v2（自主度分級，SK 2026-08-30 要求加）🟡

> SK 願景：真正嘅自我進化 agent——自己改自己 code、自己 spawn 新 agent 幫手，而唔係「建議 → 人批准」嘅半自動。
> 學界依據：DGM（self-modify code 實證 20%→50%）、ADAS（meta-agent 編程新 agent）、Digital Apprentice（per-skill 自主狀態機）、Levels of AGI（DeepMind 6 級 autonomy）、Parasuraman 2000（10 級 LOA）。
> 核心原則：**earned autonomy**——升階要「實證 + 明確人類授權事件」，agent 唔可以自己升自己；**降級自動且不對稱**（quality degrade 即降，唔使人批）。
> ⚠️ v2 修改（R10/R11/R14）：由「agent 整體分級」改為 **per-operation 分級**；L1 內分三層；eval gate 全部執行型驗證；升階條件複合化。

```
L0 ─ 而家：建議 → SK 批准 → 執行            （人手 gate；Phase A/B 就係呢級）
L1 ─ 近期：JARVIS 自己改自己嘅 harness/skills
        檔——分三層（見下）                 ← 最似 DGM / Voyager
L2 ─ 中期：JARVIS 自己 spawn subagent 做
        任務（orchestrator-worker），成果
        獨立驗證先整合                      ← 「創建 agent」落地
        **第一應用 = 報告 agent**（見下）
L3 ─ 長遠：JARVIS spawn「進化 agent」——
        唯讀研究自己 code、提改進提案，
        經返驗證 pipeline 先落地            ← full RSI 形態
```

**報告 agent（L2 第一應用，2026-08-30 SK 確認）**：
> 背景：SK 想睇報告但要睇得明——先由 Phase A prompt 改善（A0）即刻做到；報告 agent 係進化版，等 eval gate 建好先 spawn。
> 職責：將 findings 翻譯成人話 + 判斷浮唔浮出（過濾器）＋學 SK 偏好（邊啲先浮、咩格式啱睇）。
> **安全三原則（必守）**：
> ① **零權限**——報告 agent 淨係 text→text：冇工具、冇網絡、冇寫檔案權限；佢最多講錯嘢，冇能力做破壞；輸出永遠當「資料」處理，唔自動觸發任何動作
> ② **內容隔離**——俾佢睇嘅 findings 先過濾 secrets（API key 等）；findings 一律當「不可信資料」（injection 防禦：就算有惡意指令，佢冇權限執行）
> ③ **決定權喺 SK**——佢只翻譯 + 建議；所有重要決定由 SK 拍板，真正危險動作有獨立審批閘

**L1 內部分三層（per-operation，R10）**：
- **L1a sandbox 內完全自動**：filesystem + network 雙隔離（Windows 用 Docker/WSL2 等價方案）內自由行，越界即提示（Claude Code sandboxing pattern）
- **L1b 低風險 apply 自動**：skills 檔 / 文檔 / 低風險 config（YAML/JSON schema 驗證 + 語法檢查過閘）；全寫 lineage + git commit + 可一鍵 revert；超閾即轉 L1c
- **L1c 高風險人手**：任何控制邏輯 / approval gate / sandbox 設定 / evaluator / prompt 主檔 / tool 權限——**物理上喺 agent 寫入權限之外**，唔靠 prompt 約束

**每級升階條件（複合閘，唔係單一指標）**：
- **L0→L1**：① golden set（frozen、人手標註、agent 改唔到）0 regression ② 自動 apply 通過率 ≥80%（執行驗證計，唔係 LLM 自評）③ override rate 預警（<3% 參考）④ 生產-like 環境連續 2 週 + 監控 reviewer engagement（防 complacency）⑤ 自動 apply 範圍限短、細 blast-radius 操作（METR：<4 分鐘任務先 ~100% 成功）
- **L1→L2**：① L1 自動改動喺 frozen golden set + failure regression set 上連續 2 週無 regression ② 建立**獨立**子 agent 驗證機制（驗證者唔同執行者共享 prompt/model/context 弱點；整合前強制暫停 + 獨立審查——實證有害動作率低 4×）
- **L2→L3**：① golden set + 代表性長任務集（含跨 session）成功率 ≥90% ② 0 次紅線違反（0 次改 evaluator / 0 次持久副本 / 0 次未授權外部副作用）③ 獨立 safety case review 通過 ④ lineage 完整可 audit

**安全紅線（METR / DGM / Anthropic Red Team 教訓）**：
- ❌ 唔好俾 agent spawn 自己嘅持久副本（rogue agent；Anthropic Red Team 列 self-replication 為 open problem）
- ❌ evaluator / golden set / 審批規則 / 權限永遠喺 agent 觸及唔到嘅地方（immutable 存儲 + hash 驗證）
- ❌ subagent 唔可以 spawn subagent（要 spawn 就 return 俾 parent 決定）；任何 agent 唔可以改自己權限/config/紅線
- ✅ 每級都要 cost budget（token/API/cost 三層）+ lineage DAG（深度 cap 2-3 層）+ 可 revert + kill switch
- ✅ 升階單向可退回；**降級自動**——邊個 skill 退化就收回邊個 skill 權限（粒度係權限唔係成級）+ SK 一鍵全退
- ✅ 自我改進速率監控：每週自動 apply 數量/能力增長異常加速 → 自動降級 L0（METR：能力每 ~7 個月翻倍）

### Phase E — 理解確認層 v2（Clarification Gate，SK 2026-08-30 要求加）🟡

> 目的：agent 未完全理解 user 目標之前唔好開始執行，避免做錯方向浪費成本。
> 實證：主動提問確實提升任務成功率（MAC MultiWOZ +7.8%、CLAM、T2I 5 輪內 alignment +2 倍、>90% 用戶受落）——但 default LLM 幾乎唔問（>95% 直接作答）。過度提問成本高（Alexa 77% top-1 已啱；用戶答 ~11 條就疲勞；連續 >3 條問題用戶放棄）。
> ⚠️ v2 修改（R12）：**raw confidence 唔做唯一門檻**；主觸發器 = unknowns + EVPI；一輪為主、兩輪係上限；問題結構化。

**E1. 理解度自評（結構化，唔係問「有幾信心」）**
- agent 接任務後先輸出理解摘要 + 關鍵假設清單（1-5 條）
- 自評：`{unknowns: [...], assumptions: [...], confidence: 0-100}`——confidence 由「列 unknowns → 列 assumptions → 逐條評估 → 先俾分」結構化得出（P(True) 式，Kadavath），raw verbalized confidence 系統性 overconfident 唔可信
- **主觸發器**：unknowns 非空 **且** 會改變行動（EVPI：唔改變行動就唔好問；兩個答案都導致同一行動就唔好問）
- confidence 做輔助訊號：初版 threshold 80-90，記錄 logs 校準（「自評 <90 但冇問」vs「問完有冇改變計劃」）

**E2. 主動提問（一輪為主、兩輪係上限）**
- **第 1 輪**：用「最高資訊增益優先」（Active Task Disambiguation / CLAM）揀 3-5 條問題——一次過問晒，唔好逐輪問
- **問題結構化**：分類（目標含糊 / 範圍 / 優先次序 / 驗收標準 / 約束）+ 具體選項（2-5 個候選詮釋揀一，參考 Codex ask_user_question），唔好自由文字
- **第 2 輪**：只准 1-2 條 follow-up，而且要係「用戶上輪答案引伸」嘅問題；2 輪後強制 proceed
- 用戶答完 → 更新理解 → 再自評

**E3. Fallback + 執行前確認**
- 2 輪後仍唔明 → 進入「proceed-with-assumptions 模式」：「最保守假設」按任務類型定義（刪除類=唔好刪、發送類=唔好 send、生成類=最通用詮釋）+ 執行前列 assumptions 清單俾 user（一次過、可跳過）
- 高風險 / 不可逆任務：執行前將「最終理解 + 計劃」俾 user **二元確認**（具體行動描述：「要 send 俾成個 mailing list 而唔係 marketing segment？」），唔好空泛問「你確定嗎？」；或者降級 plan-only/dry-run（Anthropic Plan Mode 實證最有效 oversight）
- 低風險可逆任務：act-and-refine（自信做 + 容易更正），唔好乜都問——審批太密用戶會 tune out（Anthropic：experienced users 40%+ 用 auto-approve）

**E4. Feedback loop（v2 新增）**
- 記錄每次提問「問完有冇改變 agent 嘅計劃/行動」做 precision 指標（HiL-Bench Ask-F1 概念）
- 定期校準 threshold 同問題質量——「幾時問」係可訓練技能（RL 訓練 help-seeking 0.15% → 74%），Phase E 升級做可自我校準層

**研究備註**：ReAct 原論文冇內建確認 gate——確認 gate 係框架層外加設計（Claude Code AskUserQuestion + Plan Mode、OpenAI guardrails、LangGraph interrupt），引用時唔好聲稱「跟 ReAct 做法」。

### Phase F — 提示詞管道 v2（Prompt Formatter / Optimizer，SK 2026-08-30 要求加）🟡

> 目的：提升「agent → agent」任務發佈嘅 prompt 質素（Anthropic 實證委派描述質素直接決定子 agent 成敗）。
> 實證：LLM 可寫出勝過人類嘅 prompt（OPRO GSM8K +8%、APE 19/24 task、GEPA 勝 MIPROv2 10%+）——但**冇評分訊號就唔算優化**（純重寫效果唔穩定）；MIPROv2 一次 compile 燒 $50-500+（每次 dispatch 做真優化唔現實）。
> ⚠️ v2 修改（R13）：分 **兩層**——inline Formatter（輕量、每次 dispatch）+ 離線 Optimizer（真優化、只對高頻任務）；加 injection 防禦閘。

**F1. 兩層管道**
```
任務需求
 ├─ L1 Formatter（inline，每次 dispatch，一次 LLM call）
 │    → 結構化成 目標/背景/約束/驗收標準/輸出格式 五段（標記化版本）
 │    → 子 agent 執行 → 結果回饋（結構化驗收評分）
 └─ L2 Optimizer（離線，只對重複性高嘅任務類型）
      → GEPA 式反思進化 / DSPy compile（以驗收標準做自動評分）
      → 勝出 prompt 入 pattern 庫 → 下次命中直接用 cached（唔再 call optimizer）
```

**F2. Formatter 規則（inline）**
- 優化對象：任務 prompt（發俾子 agent 用）——**唔郁 user 指令**（信任邊界）
- 優化準則：明確目標 / 具體背景 / 可驗證交付標準 / 避免含糊指令
- 成本控制：簡單任務（預期 <N 步、無外部資料）直接用模板跳過；pattern 庫命中直接用 cached；優化呼叫行快/平模型（TextGrad 模式）
- 每次輸出可 diff 版本（lineage 可追溯）——diff 同時係 injection 偵測基礎

**F3. Optimizer 規則（離線）**
- 只對重複性高任務類型（研究 / 寫 code / 摘要）跑；以驗收標準做自動評分（檢查清單 / 格式 / 邊界）
- Pattern 庫每條記錄：適用場景、改前後 diff、實測勝負（**有分數證明先升格做正式 pattern**，唔由 LLM 自評驅動）、失效條件
- 冇評分嘅任務唔入學習 loop

**F4. Injection 防禦（v2 新增，最嚴重風險）**
- ⚠️ 優化器 = 潛在 jailbreak 入口（AdvPrompter：用 LLM 生成 prompt 本身就係攻擊手段）；double-hop injection（任務需求已含不可信內容 → 污染優化器 → 污染 prompt → 污染執行 agent）
- 安全約束以「不可變區塊」由系統注入優化後 prompt 嘅固定位置——優化器**無權改寫**（唔准越權 / 唔准改工具權限 / 唔准覆蓋 user 指令）
- 優化器冇工具權限、冇網絡權限（純 text→text）；優化輸出差異自動掃描「敏感模式」（權限 / 工具 / 輸出目的地 / 安全關鍵字），命中 → 降級用原版 + 記 log
- Instruction hierarchy 原則：system > user > 優化輸出（第三方/工具資料），低權限指令唔可以覆蓋高權限約束；高風險動作維持人手確認
- 每次優化記錄「優化器所見輸入」+「輸出」做 replay 審計

**F5. 名詞澄清（引用時）**
- Phase F 講嘅「用 LLM 優化 prompt」證據應引 OPRO / GPO / GEPA / DSPy 呢條線；Suzgun et al. 嘅「Meta-Prompting」（LLM 做 orchestrator + experts）係另一個概念，唔好混淆。
